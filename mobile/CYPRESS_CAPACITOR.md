# Cypress against the Capacitor WebView — gap + roadmap

The Cypress specs in `cypress/e2e/15-mobile-shell.cy.js` +
`cypress/e2e/16-mobile-interactions.cy.js` exercise the **SPA** that
the three Capacitor shells (student / parent / teacher) load. They
hit the same backend URLs the native shells point at via
`mobile/scripts/configure-server.cjs`, so any SPA regression that
would break the mobile experience is caught.

What they **don't** test:

| Surface | Why Cypress can't reach it today |
|---|---|
| Camera plugin (snap a doubt photo, ID-card scan) | Capacitor's `Camera` plugin shim isn't loaded in the standard Cypress browser — it lives in the native runtime. |
| Push Notifications (FCM/APNs handoff) | Same. The plugin returns a stub when run outside a real Capacitor shell. |
| Filesystem (offline-pack download to native storage) | The `Filesystem` plugin only writes to native paths; the browser has no way to assert those. |
| Background-task scheduling | iOS/Android background scheduler is a black box from the WebView. |
| App lifecycle events (pause / resume) | Generated by the OS, not the WebView. |

## What CI needs to close this

Two paths, pick whichever lands first:

### Option A — Cypress against the Android Emulator WebView

```yaml
# .github/workflows/capacitor-e2e.yml  (skeleton — needs filling in)
name: capacitor-e2e
on:
  workflow_dispatch:
  push:
    branches: [main]
    paths: ['mobile/**', 'padhai/web.py', 'padhai/home_ui.py']

jobs:
  android-emulator:
    runs-on: macos-latest  # only macos has hw-accel KVM in GHA today
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - name: Install + cap sync
        working-directory: mobile
        run: |
          npm ci
          npm run build  # configure-server.cjs + cap sync
      - name: Boot Android emulator (API 34)
        uses: reactivecircus/android-emulator-runner@v2
        with:
          api-level: 34
          target: google_apis
          arch: x86_64
          script: |
            # 1. Start a local backend on 10.0.2.2:8000 reachable from
            #    the emulator (PADHAI_REQUIRE_AUTH=0).
            # 2. Build the APK + install on the emulator.
            # 3. Run Cypress with `experimentalWebKitSupport=true`
            #    pointed at the emulator's WebView through adb-forward.
            echo "TODO: wire this up — needs:"
            echo "  • backend container on host network"
            echo "  • cypress-webview-bridge or appium-webview"
            echo "  • the actual interaction specs (see e2e/16-* for a"
            echo "    template — copy + flag .capacitor() helpers)"
```

The blocker: **Cypress cannot drive a Capacitor WebView directly.**
You either:

- Use `cypress-on-react-native` or a similar adapter
- Or use **Appium / Detox** to drive the WebView via UIAutomator (Android) /
  XCUITest (iOS), then attach Cypress only to the JS layer through a
  port-forwarded debug bridge

Either route is multi-day infra work. Out of scope for this sprint.

### Option B — Drop Cypress for Detox

[Detox](https://wix.github.io/Detox/) was built specifically for
React-Native + Capacitor end-to-end testing. It has first-class
support for:

- Native taps + gestures
- Network mocking
- Background/foreground transitions
- iOS Simulator + Android Emulator

Rewriting `cypress/e2e/16-mobile-interactions.cy.js` in Detox JS
syntax is ~1 day of work, but it removes the option-A bridge
problem entirely.

### Option C — Live with the gap

Today's coverage is:

- The SPA loads at the three shell entry URLs (15-mobile-shell)
- Interactions inside the SPA work in a browser (16-mobile-interactions)
- The Capacitor configs point at a real backend (`mobile/scripts/configure-server.cjs`)

For everything past that — camera, push, filesystem, background — we
rely on a manual QA pass before each Play-Store / TestFlight release.
This is the current state.

## When to revisit

Pick this up when one of these becomes true:

1. A native-plugin regression ships to production (we'd notice via
   crash analytics or low ratings).
2. The mobile team grows past one engineer (then the overhead of
   maintaining a Detox suite pays back).
3. Apple or Google flags a missing native-test attestation during
   review.

Until then, the SPA-side specs we already have cover most of the
real regression risk — the native plugins are thin shims and rarely
the source of bugs.
